One question.
Very different engines.

A beginner-friendly tour of VertiPaq, Databricks Metric Views and SQL Warehouses, Snowflake, and Fabric Warehouse—and how to think about concurrency.

The key distinction

Model ≠ engine

A metric definition describes meaning. A query engine does the work.

The useful question

Who runs SQL?

Find where data lives, which compute executes the query, and what serves many users.

The decision

Fit the workload

Interactive BI, a data product, an ELT job, and a busy dashboard are different problems.

Learning goal: By the end, you can explain each layer, compare the platforms fairly, and choose a concurrency strategy without confusing scale-up with scale-out.
Set expectations: the products are not all the same kind of thing. We will separate semantic modeling from storage and execution before comparing them.

01 · Start with a map

Analytics has layers.
Name the layer first.

Most confusing comparisons put a modeling feature beside a database and call them competitors.

DataFiles, tables, transactions
→
Storage formatParquet, Delta, micro-partitions
→
Query engineScans, joins, aggregates
→
Semantic modelMeasures, names, relationships
→
ConsumerDashboard, analyst, app

VertiPaq

An in-memory, columnar analytics engine used by Power BI Import models and Analysis Services tabular models.

Databricks Metric View

A governed semantic definition of measures and dimensions. It is not the compute cluster or SQL engine.

Warehouse

A SQL analytics service: storage is read by provisioned or managed compute that plans and executes queries.

Rule of thumb: “What does revenue mean?” is semantic. “How do we scan 8 TB?” is execution. “How do 2,000 viewers get answers?” is serving and concurrency.
Many architectures use multiple layers together. A BI model can query a warehouse, and the same underlying warehouse can power many different consumers.

02 · The engine inside an Import model

VertiPaq: compress columns,
answer aggregates quickly.

VertiPaq is not a cloud MPP warehouse. It is a columnar, in-memory engine optimized for analytical models.

A toy sales table
RegionNorth · South
North · North
South · West
Amount12 · 7
12 · 4
7 · 12

A row store thinks in records. A column store can read just Amount and the grouping column it needs.

What compression does
1 · DictionaryMap repeated values such as North/South to compact IDs.
2 · EncodingStore the IDs compactly; encode numeric columns efficiently.
3 · SegmentsOrganize column data into compressed chunks for scanning and filtering.
4 · Formula engineEvaluate DAX measures and relationships over the model.
Trade-off: Repeated values and a good model shape often compress well; high-cardinality columns can consume much more memory. Import refresh and model memory limits still matter.
Simplify: VertiPaq is like keeping a compact, column-oriented analytical copy in memory. It avoids reading irrelevant columns for many BI queries. Compression depends on data and does not guarantee every model is tiny.

03 · How a BI question is answered

With Import, the model
sits between the report and data.

The storage mode changes where query work happens—and therefore changes the latency, freshness, and capacity story.

SourceLakehouse / warehouse / DB
→
RefreshLoad and transform data
→
VertiPaq modelCompressed in-memory columns
→
Report queryDAX measures and filters

Import

Copy into the model. Often fast and feature-rich for interactive BI. Freshness follows refresh cadence; model size and refresh are real design concerns.

DirectQuery

Query the source. Source performance, network, and concurrent query capacity matter. The semantic model does not mean all data is imported.

Composite

Mix modes. Some tables may be imported and others queried live. Understand which query goes where before troubleshooting speed.

Important: A Power BI semantic model can be backed by VertiPaq, a live connection, DirectQuery, or a mix. “Power BI uses VertiPaq” is not true for every model and query.
A refresh is an ingestion/loading operation into the model, not the same thing as a user query. For DirectQuery, interactive concurrency can become a source workload. Always identify storage mode.

04 · Databricks Metric Views

Metric Views define meaning.
They do not replace compute.

A reusable semantic layer helps teams agree on “revenue” or “active customers” without hard-coding every definition into every dashboard.

Definition layer · Unity Catalog
SourceGoverned tables / views and relationships
DimensionsTime, region, product, customer segment
MeasuresRevenue = SUM(net_amount), orders = COUNT(...)
MEASURE(total_revenue)
GROUP BY region, month

A Metric View is a governed semantic definition (YAML-backed), queried by consumers through supported interfaces.

Execution layer · Databricks SQL
Dashboard / BI / SQLRequest metric + grouping
↓
SQL WarehousePlans and runs distributed SQL
↓
Delta tablesGoverned data in cloud storage

The SQL Warehouse supplies compute. The metric definition describes what query to run. The data still has to be read, joined, and aggregated.

Do not compare Metric Views directly to VertiPaq: one is a semantic definition; the other is a compressed in-memory execution/storage engine. A Metric View still depends on a serving engine and its workload capacity.
Metric View features and support evolve; verify current Databricks documentation for your cloud and workspace. Do not promise that a metric definition alone materializes or accelerates data—materialization and caching are separate capabilities/configuration.

05 · MPP explained without the jargon

MPP means split the work,
then bring results together.

Massively parallel processing divides a large query into tasks that can run on multiple workers at once.

1 · PlanParse SQL, choose scans, joins, filters, and aggregation strategy.
2 · DivideSplit the work by files, partitions, or data distribution.
3 · ExecuteWorkers scan and compute in parallel; shuffle may move rows between workers.
4 · ReturnCombine partial results and send rows to the caller.
SQL queryGROUP BY region
→
CoordinatorBuild plan, schedule tasks
→
Worker A · files 1–3
Worker B · files 4–6
Worker C · files 7–9
→
MergePartial sums → final answer

Scale up

Give the query more/larger compute. Useful when one query needs more CPU, memory, or I/O bandwidth.

Scale out

Add workers or clusters. Useful when work can parallelize or more independent queries need service.

Partition wisely

Parallelism helps only if data and work distribute well. Skew, shuffle, tiny files, or a hot key can bottleneck.

MPP is a design approach, not one standardized product feature or guaranteed query speed. Network shuffle and coordination have costs; adding workers is not a magic fix for a poor plan.

06 · Snowflake

Shared data.
Independent virtual warehouses.

Snowflake separates persistent storage from the virtual warehouses that execute SQL, so teams can isolate compute for different workloads.

Cloud servicesAuthentication, metadata, optimization, coordination
Virtual warehouse · BICompute cluster executing BI queries
Virtual warehouse · ELTSeparate compute for ingestion/transformation
Shared storageCompressed, columnar micro-partitions

What “independent” buys you

A heavy transformation on one virtual warehouse need not consume the same warehouse compute as dashboards on another. Compute can be resized, suspended, resumed, and governed separately.

Multi-cluster for busy periods

A multi-cluster warehouse can add clusters to handle concurrency. This is different from making one query bigger: the goal is often to serve more simultaneous queries with less queuing.

Watch the bill: More running compute clusters and larger sizes consume more credits. Autosuspend, workload isolation, and appropriate min/max cluster settings matter.
BI clusterMany dashboard requests
ELT clusterBatch transformations
Ad hoc clusterAnalyst exploration
↘
Same governed dataCompute clusters access shared storage
Snowflake is not literally “one shared disk” in the traditional database sense; its service layers coordinate access to cloud storage. Multi-cluster is mainly concurrency scaling, not necessarily faster execution for one query.

07 · Microsoft Fabric Warehouse

SQL warehouse,
inside a shared data platform.

Fabric Warehouse combines a SQL analytics experience with OneLake and Delta-format interoperability across Fabric workloads.

Simplified architecture
SQL analyticsT-SQL endpoint, query optimization, distributed execution
Fabric capacityShared capacity budget across assigned Fabric workloads
OneLake storageOpen Delta tables; shared data avoids unnecessary copies
ConsumersPower BI, notebooks, pipelines, SQL clients

Why teams choose it

T-SQL familiarity, managed warehouse experience, OneLake integration, and close Power BI/Fabric workflows. Shared data can reduce duplicated copies between lake and warehouse patterns.

What capacity changes

Fabric uses distributed query processing: a frontend plans SQL and a DQP engine schedules work across backend nodes. Backend compute can scale autonomously with demand, but this is not a promise of subsecond startup for distributed queries.

Workload management separates SELECT and non-SELECT work into resource pools by default, helping isolate reads from ingestion. Capacity SKU guardrails, concurrent tasks, and service behavior still affect latency.

Plan for: capacity sizing and monitoring, workload scheduling/isolation, SQL tuning, and the exact behavior of your SKU and current Fabric features.

Not just a Lakehouse

Warehouse provides a SQL-first warehouse authoring and serving experience.

Not just Power BI

Warehouse SQL execution is distinct from a VertiPaq semantic model, even when Power BI sits on top.

Not a free performance switch

OneLake interoperability does not remove modeling, capacity, concurrency, or query tuning choices.

Fabric's current workload-management docs describe task scheduling, autonomous backend scale, default read/write pool isolation, and limits/guardrails. Check the linked docs for the current details and SKU guardrails. This deck avoids hard-coded concurrency limits.

08 · Databricks SQL Warehouse

SQL compute over lakehouse data,
with a semantic layer available.

A Databricks SQL Warehouse is a compute resource for SQL workloads. Metric Views can define business metrics queried by that compute.

The request path
BI dashboard / SQL clientSubmits SQL, possibly using a Metric View
SQL WarehouseServerless, Pro, or Classic options (availability varies)
Distributed executionPlans and executes query tasks across compute
Unity Catalog + DeltaGovernance, metadata, permissions, lakehouse tables

Concurrency knobs

Warehouse size: More compute can help resource-heavy queries. Cluster scaling: Additional clusters can serve concurrent demand. Serverless: Managed startup/scaling experience where available and enabled.

What it is not

A Metric View is not a warehouse. A SQL Warehouse is not the Metric View. The lakehouse table is not the serving compute. Keep those responsibilities separate when diagnosing latency.

Measure the actual bottleneck: startup, queue time, scan volume, shuffle, skew, concurrency, source layout, and caching are different causes with different fixes.

10 · Concurrency, in plain language

High concurrency means
many requests at once.

It is not the same as a single query over a very large dataset. Ask whether users are waiting in a queue or one query is intrinsically slow.

Scale-up: help a heavy query
1 large queryNeeds CPU / memory / I/O
→
Bigger computeMore resources per execution

Good when elapsed time is dominated by a resource-bound scan, join, or aggregation and the plan can use the added resources.

Scale-out: serve more at once
Many queriesUsers / dashboards arrive together
→
More clusters / capacityMore parallel service slots

Good when concurrent demand creates queuing and the platform supports adding compute for that workload. It can cost more.

First: inspect queue time

A slow query with little queue time points to query/data/compute work. Large queue time suggests contention, admission control, or insufficient serving capacity.

Then: isolate workloads

Separate BI from ELT or ad hoc work where the platform supports it. A predictable dashboard should not compete blindly with an overnight rebuild.

Finally: right-size

Tune model, SQL, file layout, caching, schedules, autosuspend, and scaling together. More concurrency can increase cost and still leave a bad query slow.

For VertiPaq, think model-serving capacity and BI capacity/refresh concurrency, not adding MPP warehouse clusters. DirectQuery sends work to its source, so source concurrency becomes important.

11 · Choose by workload

What would you pick?
Try a few realistic starting points.

Choose the closest scenario. Treat the answer as a shortlist—not a product ranking.

Starting point · Fast interactive BI

Consider an Import semantic model when it fits.

Curate and refresh the model, define measures centrally, and test model size and refresh time. If data freshness or size rules Import out, evaluate DirectQuery/composite and capacity carefully. Do not select Metric Views as a substitute for BI serving compute.

Measure: visual latency, refresh duration, model memory, and concurrent viewers.

Always validate: data volume and growth, freshness target, SQL/BI skills, governance, cloud and region availability, capacity budget, and real concurrent query patterns.
Invite learners to justify a choice using requirements. Multiple platforms can satisfy the same need; the right choice is constrained by existing governance, skills, workload, and economics.

12 · The takeaway

Remember these five things.
Then go test your workload.

1. VertiPaq is a compressed, columnar in-memory analytics engine—not a general-purpose cloud MPP warehouse.

2. A Databricks Metric View centralizes metric meaning; Databricks SQL Warehouse supplies query compute.

3. Snowflake warehouses, Fabric Warehouse, and Databricks SQL Warehouses are SQL analytics services with different storage, governance, and scaling models.

4. MPP divides query work across workers; more workers help only when the query and data can use them.

5. Scale up for a slow resource-bound query. Scale out/isolate for concurrent demand and queueing—then watch cost.

First diagnostic question: Is the time in the queue, the query, data movement, or the consumer?
